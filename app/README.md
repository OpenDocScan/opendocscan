# OpenDocScan for Android and iOS

The Flutter shell around the same Rust core the web app runs. This is **M1**:
a photograph, taken or imported, crosses into `docscan-core` and comes back
measured. Detection, correction, filtering and PDF export are M2 and are not
wired up here yet — the core already does all of them, and the web app drives
them today.

```
app/                     this Flutter project
  lib/
    main.dart            loads the Rust library, then runs the app
    home_screen.dart     capture or import, and the results
    capture/             the viewfinder, behind a fake-able controller
    import/              the file picker, behind an interface
    permissions/         permission checks, behind an interface
    scan_result.dart     the three outcomes: pending, decoded, failed
    theme.dart           the design tokens, as Dart
    src/rust/            GENERATED by flutter_rust_bridge — never edit
  rust_builder/          GENERATED by cargokit — never edit
../crates/docscan-ffi/   the Rust side of the bridge
```

## Running it

```sh
flutter run                       # a connected device or a running simulator
```

The Rust core is cross-compiled automatically by cargokit as part of the
Gradle and Xcode builds. No separate step.

## Tests

There are two suites and they prove different things. Running only one of them
gives false confidence, in both directions.

```sh
flutter test                                              # 20, no device
flutter test integration_test/bridge_test.dart -d <id>    # 6, on a device
```

`test/` fakes the bridge, because `flutter test` runs on the Dart VM where a
library built for a phone cannot be loaded. So it proves the **screens** are
right — every permission state, a cancelled pick, one bad file among good
ones — and proves nothing at all about the bridge.

`integration_test/` is the other half: it loads the real `.so`/`.framework`,
calls the real core, and is the only thing that catches a broken
cross-compile, a missing ABI, or codegen that drifted from the Rust.

Verified on an Android emulator (API 35, arm64) and the iOS Simulator, plus a
manual pass importing a real page through the system photo picker.

## Regenerating the bridge

After changing anything in `crates/docscan-ffi/src/api/`:

```sh
flutter_rust_bridge_codegen generate
```

## Three traps, all of which cost real time here

**The FFI crate is `docscan_ffi`, with an underscore, where every sibling
crate is hyphenated.** cargokit reads `[package] name` verbatim and then looks
for `lib<name>.so`, but Rust writes `libdocscan_ffi.so` — it converts hyphens
to underscores. Named `docscan-ffi`, cargokit builds the library, looks for a
file that does not exist, and copies nothing **with no error at all**: the
Gradle task reports success, the `jniLibs` folders are created and left empty,
and it surfaces much later as `dlopen failed: library "libdocscan_ffi.so" not
found` at startup.

**`permission_handler_android` is pinned in `dependency_overrides`.** 14.0.0
and 14.1.0 both set `compileSdk = 37`, and there is no released Android
platform 37 — `sdkmanager` offers 36 at most. The failure is `Failed to find
target with hash string 'android-37'`, which reads like a broken local SDK.
Lift the pin once 37 ships.

**The core's `image` dependency has `default-features = false`.** The web build
needs PNG for fixtures and JPEG for PDF export; the phone needs **JPEG decode**,
because that is what a camera hands over. Trimming the feature list to what the
browser needs would break capture on both platforms, and
`integration_test/bridge_test.dart` has a test that fails when it happens.

## Known gaps

- **HEIC is not decodable.** Capture goes through the camera plugin and arrives
  as JPEG, but a file picked out of an iPhone's Photos library may be HEIC. It
  surfaces as "Could not read this image", not a crash.
- **No real-hardware pass yet.** An emulator has no camera worth the name and
  the iOS Simulator has none at all, so the capture path is proven by fakes and
  by the plugin's own behaviour, not by a photograph taken on a phone.
